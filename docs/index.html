Can a search service choose its own index?

Search systems are normally told which strategy to use at deploy time. That decision is correct on the day you make it and progressively wrong afterwards. This is a Go prototype that moves the decision into the running system — re-selecting its index backend, its cache lifetime and its warm set from live dataset characteristics.

01The question

You decide up front that a corpus is “small” and belongs in an in-process index, or “large” and belongs in Elasticsearch. That gets baked into config. But datasets grow, go dormant, get rewritten and change shape independently of your deploy cycle — so the configuration drifts away from reality.

The investigation asks what happens when that decision moves out of config and into the running system: which signals are cheap enough to drive it, and what breaks when a system is allowed to change its own mind?

Two things mattered more than expected, and both shaped the code:

  • Getting the signal cheaply is the hard part, not acting on it. The obvious implementation reads COUNT(*) per dataset on the query path — an O(n) scan that dominates everything else. It is replaced by a trigger-maintained counter table for an O(1) read.
  • A system that reacts instantly oscillates. A dataset sitting on a tier boundary flaps between backends on every write, and each flap costs an index rebuild. Adaptation needs damping to be worth anything.

02What “adaptive” concretely means

Three independent mechanisms, each driven by observed behaviour rather than configuration. This is the substance of the prototype.

1 Index tier, by size

The profiler reads the O(1) record count and maps it to a tier, each with its own engine and fallback chain. Thresholds are configurable.

TierRecordsEngine
small< 100KBleve in-memory
medium100K – 5MBleve file-backed
large≥ 5MElasticsearch

The damping is the interesting part: an upgrade requires the dataset to be observed above the threshold for 5 consecutive evaluations before it commits. Downgrades are immediate. A dataset hovering at exactly 100,000 records stays put instead of rebuilding on every write.

2 Cache TTL, by volatility

Every dataset carries a stability score in [0, 1], maintained by a monitor ticking once a minute:

  • A quiet cycle adds 0.05 — linear recovery.
  • A write multiplies by 0.80 — geometric punishment, so a burst collapses the score fast while one write barely dents it.
  • At ≥ 0.70 the dataset counts as stable.

That score picks the cache lifetime directly: 10 minutes for a stable dataset, 30 seconds for a volatile one. Nothing declares a dataset stable — it earns the longer TTL by not changing.

3 Warm set, by access history

Every search appends to an access log on a fire-and-forget goroutine. At startup the service preloads the 50 most-recently-accessed datasets and builds their indexes before accepting traffic.

The warm set is therefore derived from real usage rather than a hand-maintained list, and rows older than 30 days are purged by the background reconciler.

A read-your-own-writes guard sits on top. Any write stamps a 30-second flag in Redis, and while it exists the search path skips both cache layers entirely rather than risk serving a stale result to the client that just wrote.

03Architecture

PostgreSQL is the only source of truth. Every search engine is a derived, disposable index that can be rebuilt from it — and Redis, Elasticsearch and Kafka are each individually optional.

04Method & measurement

Reproducibility is the point of a research artifact, so the instrumentation is the most reusable part of this prototype.

Thirteen Prometheus metrics are exposed on /metrics, and four Grafana dashboards are auto-provisioned from the repository — API Overview, Search Performance, Write Pipeline and System Health.

Three of those metrics carry the experimental weight:

MetricLabelsWhat it tells you
dataset_tier_transitions_total from_tier, to_tier The direct record of adaptation firing, and in which direction
search_duration_seconds tier Latency per tier — pair with the above to see if a transition helped
cache_hits_total / misses layer (L1/L2) Whether the volatility-driven TTL is actually earning hits
reconciler_drift_detected_total — How often PostgreSQL and Elasticsearch genuinely diverged
upsert_records_total status Includes skipped — checksum-idempotent writes that did nothing

Tests

70 tests and 11 benchmarks across 14 files. The chaos tests need no database and target concurrency properties directly — LRU eviction under 10× capacity pressure, and simultaneous insert/delete against the B-Tree index to prove the absence of data races. They are close to meaningless without -race.

The DB-backed tests skip silently unless TEST_POSTGRES_DSN is set. A green go test ./... on a machine with no database does not mean the integration suite passed. CI runs it in a dedicated job against a PostgreSQL 16 service container so the default-skip cannot hide a failure.

What was not measured

The 11 benchmarks are micro-benchmarks — cache get/set, Bleve search over 100 and 1,000 documents, fuzzy versus exact query cost, and the SHA-256 helpers. No benchmark results are committed to the repository, and none are quoted here, because any numbers they produce are specific to the machine that ran them.

More importantly, there is no benchmark of the adaptive tiering itself — nothing measures what a tier transition costs, or whether the chosen tier beats the alternatives at a given corpus size. That is the obvious next experiment and it has not been run.

05Run it yourself

Only PostgreSQL is required. Redis, Elasticsearch and Kafka are each optional, and the service degrades gracefully without them — which makes for a much lighter loop than the full stack. 

# Clone and configure
git clone https://github.com/iampopye/IMI_Hackathon.git
cd IMI_Hackathon/search-system
cp config/config.yaml.example config/config.yaml
# replace the two CHANGE_ME placeholders with searchuser / searchpass

# Minimum viable stack — or `docker compose up -d` for everything
docker compose up -d postgres redis
go run ./cmd/server

curl localhost:8080/health          # {"status":"healthy"}

Migrations run automatically at startup. To watch the adaptation, search the same dataset twice — the response’s engine field gains a +mem_cache or +redis_cache suffix on the second call. Write to the dataset and search immediately instead, and the RYOW guard bypasses the cache entirely.

06What this is not

A research prototype earns credibility by being precise about its limits. These are real, and stated here so nobody discovers them the hard way.

Not production-hardened

  • No authentication or authorisation on any endpoint. Anyone who reaches the port can read, write and delete every dataset.
  • CORS is Access-Control-Allow-Origin: *, hardcoded.
  • Development credentials throughout the Compose stack, and sslmode=disable.

Not proven at scale

  • The 100K and 5M thresholds are design parameters, not empirical findings — plausible boundaries, not derived from measurement.
  • It has never run against a 5M+ record corpus, so the large tier and its Elasticsearch path are the least exercised code in the repository.

Known incomplete

  • performBTreeBuild is an explicit no-op stub. The advisory-lock coordination and state machine around it are real and working; the sort it guards does nothing.
  • The concurrent B-Tree index is tested but not wired into the query path.
  • Hysteresis counters are per-process and in-memory — they neither survive a restart nor coordinate across replicas.

What you should and should not conclude. This demonstrates that runtime-adaptive index selection is implementable with cheap signals — a trigger-maintained counter, an access log, and a decaying volatility score — and it shows the specific failure mode, oscillation, that any such system must solve. It does not demonstrate that adaptation outperforms static configuration, because that comparison was never measured. Anyone tempted to cite this as evidence that adaptive tiering is faster should run the missing benchmark first.

Origin. This was built as a hackathon project, single-author, inside a time-box. That constraint explains its shape: the mechanisms that answer the research question are built out properly and instrumented, while the parts that only matter in production are stubs or absent.
